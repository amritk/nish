# WP18 G6 — generic constraints

## Context

Generic functions (G3/G4), classes and interfaces (G5) and the whole-program rule (G7) have landed. G6 is the next item in [§16 of wp18-generics.md](../../docs/wp18-generics.md). Today:

- [self/parser.ts](../../self/parser.ts) `parseTypeParameters` refuses `extends` in a type-parameter list with "a constrained type parameter (`T extends ...`) is not supported yet" ([tests/cases/reject_generic_constraint.ts](../../tests/cases/reject_generic_constraint.ts)).
- **Member access on an unconstrained parameter is accepted by accident.** A template body is checked once for each instantiation, with `T` bound to the concrete type in `ctx.typeBindings` ([§15.1](../../docs/wp18-generics.md), "A type parameter is never a type"). So `const getX = <T>(p: T): i32 => p.x;` compiles today at `T = Point`, and the error only shows up at an instantiation whose `T` has no `x`. This is duck typing through monomorphisation, and WP18 §6.5 and §8 message 8 rule it out.
- Nish has no class inheritance (`extends` on a class is refused in [self/structs.ts](../../self/structs.ts)), and interfaces have fields only. So "satisfies `Shape`" means the type argument **is** `Shape`, or is a class whose `implementsNames` includes `Shape` (the prefix-layout rule, WP25). §6.5's `isSubclassOf` has no counterpart here.

## Approach

| Decision | Choice | Why |
| --- | --- | --- |
| What a constraint may name | A declared class or interface, or an instantiation of a generic one written with concrete type arguments (`T extends Container<i32>`). Anything else is refused with its own message: a scalar, `string`, an array, `Result`, another type parameter, or an instantiation that mentions a type parameter (`U extends Box<T>`). | Keeps G6 small. An F-bounded or parameter-dependent bound is a trait-system question, which §13 puts off this path. |
| Where member access is judged | Against the **constraint's** members, not the concrete type's. It is refused on an unconstrained parameter (message 8), and it is refused on a constrained one when the constraint lacks the member, even if the concrete type argument has it. | Otherwise the constraint is decorative. The mechanism is the worker's choice, but it must not depend on the concrete type: see Member access. |
| Where satisfaction is checked | At each instantiation request (inferred call, `new Box<X>`, an annotation `Box<X>`), reported at the request site in the asker's module (`RequestSite`). | §6.5: the request site is where the user wrote, or implied, the type argument. |
| Lowering | Unchanged monomorphisation. `f<T extends Shape>` at `T = Circle` reads `%struct.Circle` fields and calls `@Circle.m` directly, with no bitcast to `Shape` and no vtable. | §6.5. Because `Shape`'s fields are `Circle`'s first fields, the field index is the same either way. |
| What is untouched | Everything on a type parameter other than member access: pass on, return, store, `===`, operators that work at the concrete type (`add<T>(a, b)` at `i32` and `f64`). | This is not a template type-check. Only member access becomes constraint-bound. Every existing `gen_*` golden stays byte-identical. |
| Breaking | Yes. Programs that read a member of an unconstrained parameter stop compiling. The commit is `feat(checker)!:`, with a `BREAKING CHANGE:` trailer that names the fix (`<T extends X>`). | Before 1.0, a breaking change moves the minor version, which a `feat` does anyway. |

`self/` does not use the construct (the rolling freeze), so the bootstrap input is unchanged.

## Parsing

- `parseTypeParameters`: after the identifier, `extends` parses a type into the list instead of reporting. The node shape is the worker's choice, with one constraint: every existing reader of `children[4]` / the type-parameter list must still see the names at the same positions (for example, one child per parameter, each carrying an optional constraint child). A default (`= ...`) is still refused, unchanged.
- `startsArrowDeclaration` skips the type-parameter list by counting angle brackets. `<T extends Box<Box<i32>>>` puts `>>` (and `>>>`) in that list, so the skip has to count the split tokens the same way `expectTypeArgumentEnd` does.
- Classes and interfaces: whatever path parses `class Box<T>` / `interface Pair<A, B>` reaches the same list, so both accept constraints too.

## Resolving the constraint

- At the template (pass 1, where G5 collects templates), resolve every constraint annotation once, in the template's module, with no bindings in scope. Refuse anything outside the table above, at the constraint's span, once per template, never once per instantiation.
- Store the resolved constraint where both the function path (`Instantiation`/`bindings` in [self/generics.ts](../../self/generics.ts)) and the struct path ([self/structs.ts](../../self/structs.ts)) can read it. Cross-module: a constraint names a type in the **template's** module, so an imported template carries its constraint with it. G7's `registerForeignLayouts` may have to reach the constraint's layout. Pin this with a `tests/link/` case.

## Member access

- Field read, field write and method call on a receiver whose type came from a type parameter `T` are answered from `T`'s constraint: a field or method `Shape` does not declare is refused. The existing member messages in [self/members.ts](../../self/members.ts) apply, with `T` named alongside the constraint.
- On an unconstrained `T`, message 8: `` Cannot read `x` of `T`: an unconstrained type parameter has no members; say which ones it has with `<T extends Point>` ``. Word the method-call form in the same voice.
- **The correctness trap.** Types are concrete during an instantiation's check, so "the receiver's type is `Point`, which is `T`'s binding" is **not** a test for "came from `T`". `<T>(p: T, q: Point): i32 => p.x + q.x` at `T = Point` must refuse `p.x` and accept `q.x`. The worker picks the mechanism (for example, per-node provenance recorded when an annotation resolves through `ctx.typeBindings`, or a one-off check of the template body with each parameter bound to its constraint or to an opaque memberless type) and writes the choice and its reason in §15.6. It must satisfy all four of these:
  1. An error is reported once per template, not once per instantiation. It is reported even when the template is **never** instantiated, if the chosen mechanism checks at the template. §15.6 says which.
  2. A local inferred from a `T`-typed value (`const q = p;`) is still `T`-typed for this rule.
  3. `T[]` elements and `T | null` narrowed to `T` are `T`-typed receivers too.
  4. `Box<T>`'s own methods reading `this.value.x`, where `value: T`, go through the same rule.

## Satisfaction

- Check at every instantiation request, for the function path (inferred call) and the struct path (`new Box<X>(…)`, an annotation `Box<X>`, a field or base naming `Box<X>`). Passes: `arg` is the constraint's struct, or `arg` is a class whose `implementsNames` contains the constraint interface.
- Message 1, in §8's words with the pieces filled in: `` `T` of `sorted` requires `T extends Comparable`, and `i32` does not implement it; pass a class or interface that declares `implements Comparable` ``. When the constraint is a class, the fix clause names the class, because nothing but the class itself satisfies it.
- A type argument that is itself a type parameter of the requesting template (`g<U extends Shape>` calls `f<T extends Shape>(u)`): satisfied when `U`'s constraint satisfies `T`'s. Checking the concrete binding is also sound, but reports per instantiation. §15.6 records which the worker chose.
- Termination (G4) and the instantiation cap run unchanged. A refused request answers with the same recovery §4a gives every other refused request.

## Migration

Grep `tests/`, `std/`, `examples/` and `docs/` for member access on a value whose annotation is a bare type parameter. Each hit gets a constraint (and, where needed, an `implements`) so that its IR stays **byte-identical**. A hit whose IR would change is a finding and gets reported in the PR body, not re-goldened silently. If `std/` needs a change, that is outside this stage's Owns: stop and say so in the PR body.

## Flaky scratch files

Added at the owner's request during the run (2026-09-23T05:10Z). #157's CI failed on `differential: native and Node agree` for `cases/io_nish_import_global` alone. Native printed `argv: true` as its first line, where Node printed `imported`. `tests/cases/io_nish_import.ts` and `io_nish_import_global.ts` both write and then read `build/test/io_nish_import.txt`, and `tests/differential/run.js` runs programs through `lib.pool` with up to 8 jobs. When one twin truncates the file while the other is reading it, the read comes back empty.

- **Reproduce first** (`/debug`): run the differential runner with high `--jobs` in a loop until the mismatch shows, or write a small stress harness. A fix for a race nobody reproduced is a guess.
- **Fix the root cause, not the one pair.** Prefer isolating each program run, for example a per-program working directory that `build/test/...` resolves under, in both `tests/differential` and the golden runner(s) (`tests/run.js`, `tests/pool.js`, `tests/nish/run.ts` if they execute programs in parallel). Giving the twins different paths is not enough on its own: `tests/run.js:519-534` requires their IR to be byte-identical, so a different path string would break that check unless the comparison is taught about it.
- **Audit**: every `build/test/...` path in the corpus (`io_files`, `io_mkdir`, `io_nish_rename`, `io_readdir_null`, `io_streams`, `tests/differential/corpus/io_*`) is checked for sharing, and the native and Node runs of one program are checked for overlap.
- Add a regression guard if a cheap one exists, for example a check in `tests/run.js` that no two corpus programs name the same scratch path.

**Owns:** `tests/run.js`, `tests/pool.js`, `tests/differential/**`, `tests/nish/run.ts`, `tests/cases/io_*`. It does not overlap #157's actual diff, which touches no `io_*` case and none of these runners.
