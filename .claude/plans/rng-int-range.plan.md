## Context

[`std/random.ts`](../../std/random.ts) has `Rng` with `nextI32()` (32 bits) and `nextF64()` ([0, 1)). A program that wants a die roll writes `1 + ((r.nextI32() >>> 1) % 6)` — the idiom the module JSDoc, [`docs/LANGUAGE.md`](../../docs/LANGUAGE.md#random-numbers-rng-in-nishrandom), [`docs/cookbook/std-random.ts`](../../docs/cookbook/std-random.ts) and [`tests/link/std_random/main.ts`](../../tests/link/std_random/main.ts) all show. It is biased (2^31 is not a multiple of 6) and every game rewrites it.

## Approach

| decision | choice | why |
| --- | --- | --- |
| name | `nextInt(lo: i32, hi: i32): i32` | sits beside `nextI32` / `nextF64`; reads as `r.nextInt(1, 6)` for a die |
| bounds | inclusive at both ends | a die is `nextInt(1, 6)`; inclusive also lets the full `i32` range be asked for, which half-open cannot express |
| `lo > hi` | `panic("Rng.nextInt: lo is greater than hi")` | an empty range has no answer; the std modules panic on a caller's contract violation (`std/base64.ts`) |
| bias | none — rejection sampling on 32-bit draws | the span `hi - lo + 1` taken as an unsigned 32-bit count; draws in the low `2^32 mod span` are drawn again, the rest reduced mod span. At most half the draws are refused for any span, so the expected draws per answer are under 2 |
| full range | `nextInt(-2147483648, 2147483647)` answers `nextI32()` | the span wraps to 0, which stands for 2^32 |
| same bits under Node | only operations whose 32-bit result is defined both ways | wrapping ops come from `nish:unsafe`, unsigned compare and remainder must answer the same bits in JS as natively (`docs/RUN_UNDER_NODE.md`); no `i64`, no float |

How the unsigned arithmetic is spelled (a `u32` local, `>>> 0`, or `nish:unsafe` helpers) is the worker's call, provided the result is the same under Node and the emitted IR has no overflow check on the hot path. A single answer consumes one `nextI32()` step when not rejected, so a sequence is still reproducible from the seed.

## Next int

In [`std/random.ts`](../../std/random.ts), after `nextF64`:

```ts
/** An integer in [lo, hi], each with equal chance; panics when lo > hi. */
nextInt(lo: i32, hi: i32): i32
```

The JSDoc says: inclusive bounds, unbiased by rejection, how many steps it may take, the panic, and that the full `i32` range is allowed.

## Tests

Mirror [`tests/link/std_random/main.ts`](../../tests/link/std_random/main.ts), which already runs natively and under Node and compares both to `expected.out`:

- a fixed sequence of `nextInt(1, 6)` from a fixed seed, printed — pins the bits both ways;
- `nextInt(5, 5)` is 5 and steps once; `nextInt(-3, 3)` stays in range;
- the full range `nextInt(-2147483648, 2147483647)` equals `nextI32()` from a twin generator;
- a span just above 2^31 (e.g. `nextInt(0, 2147483647)` and `nextInt(-2147483648, 0)`) stays in range — the rejection threshold is largest there;
- bias: 60,000 draws of `nextInt(0, 5)` land within a stated tolerance of 10,000 each, and a span of 3 · 2^30 (where modulo bias is 2:1) splits its thirds evenly within tolerance — a test the `>>> 1 % n` idiom fails;
- negative: `lo > hi` panics with the documented message, natively and under Node (mirror how `tests/run.js` checks an existing std panic).

Regenerate `tests/link/std_random/*.ll`, `tests/self/goldens/checked/` (`node tests/self/goldens.js --update`) and differential goldens with the repo's tooling; never hand-edit them.

## Out of scope
