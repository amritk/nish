## Writing a guide page

The [user guide](guide/index.md) is the part of these docs written for people
who write programs in Nish. A page there follows these rules:

- **The reader writes programs, not the compiler.** Explain what a construct
  does and how to use it; leave the IR, the checker and the runtime's layout
  to the reference. No internal vocabulary: stage0, the seed, Nish-0 and work
  packages do not appear.
- **Examples are compiled.** A program is a fence marked for compilation —
  ` ```ts nish:ok `, `nish:ok-body` (wrapped in a `main` body),
  `nish:err CODE` or `nish:err-body CODE` (must be rejected with that code) —
  and `node tests/run.js guide` compiles it. Every page but
  `installation.md` carries at least one once it is more than a stub (its
  title and one paragraph). A fragment that cannot compile on its own is a
  plain ` ```ts ` block, and short.
- **The reference is normative.** Each page links the
  [LANGUAGE.md](LANGUAGE.md) section that governs it and describes nothing
  that section does not say; where the two disagree, the guide is wrong.
- **No links to the compiler's records**: not to `wp*.md`,
  `MASTER_PLAN.md` or `.claude/`.
- **Link pages relatively, everything else on GitHub.** The site serves
  every file `scalar.config.json` routes: the guide, the reference pages
  (`INSTALL.md`, `std/README.md`, ...) and the security records.
  `LANGUAGE.md` is not one of them yet, so it is linked on GitHub too. A
  relative link from a routed file to another opens it on the site, as it
  does on GitHub. A relative link to any other file — a source
  file, a test, a design note — the site serves as a download, so a routed
  page links one as `https://github.com/amritk/nish/blob/main/<path>`
  (`tree/main/` for a directory), anchor and all. `node docs/check-links.mjs`
  checks those URLs against the files here and refuses the relative form.
- **An anchor lands on both sites.** The site spells some heading IDs
  differently from GitHub (it drops the doubled and leading hyphens of
  `` `--fix` `` and keeps the dot of "4. Exit codes") and gives a heading
  below level 4 none. A link between routed pages to such a heading needs
  `<a id="<github-slug>" style="scroll-margin-top: 65px"></a>` on its own
  line above it; the style keeps the heading clear of the site's header, and
  GitHub drops it. `node docs/check-links.mjs` names each anchor that needs
  one.
- **Every page has a route.** The site's navigation is
  [`scalar.config.json`](../scalar.config.json) at the repository root, read
  by [Scalar Docs](https://scalar.com/products/docs); a new page gets a route
  there, and `node docs/check-links.mjs` fails on a page no route reaches or a
  route to a missing file. Only the `/reference` routes below are generated;
  every other route is written by hand, the "Security records" group under
  `/security` with its sub-groups included, so a new record gets its route
  there by hand, beside its index row.

## The library reference

`docs/reference/` is generated, never edited by hand: change the source's doc
comments and run `node scripts/gen-reference.mjs`, which rewrites every page
and the `/reference/library`, `/reference/language` and
`/reference/compiler` routes in `scalar.config.json` (the last two with a
route per spec section and per diagnostics band), and puts the `/reference`
group's children in order, leaving every other line of that file as
written. CI runs it with `--check`, which writes nothing and
exits 1 naming each stale, missing or extra page and a stale route; each page
opens with a comment saying so. TypeDoc reads the sources in-process, and
`scripts/typedoc-nish-widths.mjs` keeps each type as the source spells it
(`i32`, not `number`).

**Every public declaration is documented.** A function, class, constructor,
interface, method, property, accessor, variable, type, enum or enum member that
`std/` exports or `runtime/nish.d.ts` declares needs a doc comment, a `@param`
for each parameter (a constructor's, a setter's and a call signature's
included), and a `@returns` when it returns anything but `void` or `never` (a
getter's included; a constructor's is not asked for). `--check` fails on each that lacks one, naming it as
`module.Name.member` (no doc comment), `module.Name#param:p` or
`module.Name#returns`. The gaps that predate the rule are listed in
[`scripts/undocumented.txt`](https://github.com/amritk/nish/blob/main/scripts/undocumented.txt),
which only shrinks: `--check` also fails on a line that is no longer a gap.
To clear a line, document the declaration and delete the line, or run
`node scripts/gen-reference.mjs --update-baseline`, which rewrites the file
from the sources and refuses to add a line: it names each new gap, to be
documented instead. Only a change to the rule itself, one that finds gaps
that already existed, runs `--grow-baseline` to add them; its PR lists the
added lines and the reviewer reads each.
Members TypeScript's `lib` merges into a `runtime/nish.d.ts` global are not
checked.

- **Pages.** A page's title is its module specifier as a plain heading,
  its colon escaped (`# nish/json`, `# nish\:secret`, which Scalar would
  otherwise cut at the colon). `std/<path>.ts`, imported as `nish/<path>`, is
  `docs/reference/<path>.md`; the builtin module `nish:<name>` is
  `docs/reference/nish-<name>.md`, made from `std/<name>.ts` for the two
  with source behind them (`nish:region`, `nish:secret`: the compiler
  refuses `nish/region` and `nish/secret`); the globals `runtime/nish.d.ts` declares are
  `docs/reference/builtins.md`. `index.md` opens with a short lead and a
  card for the language specification, the builtins, each area of the
  standard library, the command line and the diagnostics, then lists every
  module, the standard library's grouped by area.
- **The language specification.** `language.md` is the text of
  `docs/LANGUAGE.md` before its first `##` heading, with a card per
  section; each `##` section is `language/<slug>.md`, its headings raised
  one level so the section's is the page's title. Every link into the spec
  is rewritten to the page that holds its heading, and a heading whose ID on
  the page differs from its ID in the whole file gets an `<a id>` with the
  old one, so no anchor breaks.
- **The template.** One heading scheme: the title is the only `#`, each kind
  of member (Functions, Classes, Interfaces, Objects, Types), Limits and
  Constants is a `##`, and each member a `###`; its parameters and return
  are fields, not headings. A class's or interface's members are a table;
  in a member's cell, paragraphs are a blank line apart and each list item
  starts a line of its own. A list opens a paragraph, follows a line ending
  in a colon, or continues after an item and its continuation lines. A line
  opening with `- ` or `1. ` anywhere else is prose that wrapped there, so a
  list after a line like `One of` joins into one sentence. The colon must end
  the line itself: one inside markup, as in `**Values:**` or `` `x:` ``, does
  not count. Below the lead and the usage example, a grid of cards links each
  function, class, interface and object, one icon per kind (a function, a
  cube, a hash for a constant), when the page has more than one; a section of
  constants with one card shows it without a grid. A card's title may break
  after a lower-case letter before a capital or after `_`, so a long name fits
  a 390-pixel screen. A section with nothing in it is not written.
- **The sidebar.** `/reference/library` lists the overview, the builtins,
  then the standard library by area, in `AREAS` in
  `scripts/gen-reference.mjs`, each entry titled with its module name
  (`regex`, `tls`) rather than its specifier. A module in no area fails the
  run. An area's group keeps its modules' routes
  (`/reference/library/regex`), so no link moves. The rest of the
  `/reference` group (the standard-library overview, Running under Node,
  Installing, Benchmarks, Changelog) is written by hand and placed after the
  generated groups.
- **Members.** Every exported function, class, interface, type and constant
  is on its module's page, with its signature as written. Its doc comment's
  text is its description; a member without one is shown with its type
  only. A `nish:` module's member without a comment of its own takes the
  comment of the global of the same name, whose signature it shares.
  A global that merges with a TypeScript lib declaration (`Array`,
  `String`, `Symbol`) shows only the members `runtime/nish.d.ts` declares.

- **Constants.** A constant is a limit, listed under `## Limits`, when the
  first sentence of its doc comment states a bound: it opens with "The"
  and one of "most", "fewest", "least", "longest", "shortest", "largest",
  "smallest", "deepest", "highest", "lowest", "maximum" or "minimum"; with
  "At most", "At least", "Most" or "How deep(ly)"; or with "How many", "How
  much", "How long" or "How far" and uses "may", "keep(s)", "kept",
  "hold(s)", "held" or a form of "refuse". Every other constant, a protocol
  identifier named `MAX` (`QUIC_TP_MAX_DATA`) included, is under
  `## Constants`. A constant's card is titled with its value as written,
  decimal digits grouped (`1,048,576`, `0x0e`, `"h3"`); only a constant with
  no literal value, a `runtime/nish.d.ts` declaration or one computed from
  others (`DNS_MAX_ANSWERS * 2`), is titled with its name.
- **Overloads.** Each signature of an overloaded function is shown whole, in
  source order: its own description (or the first's, when it has none), its
  signature, parameters and return. A description the first signature
  already shows, word for word, is not printed again.
- **Links.** A `{@link}` that names nothing fails the run, `--check`
  included.
- **The compiler reference.** `command-line.md` is `nish --help` as a
  page: `helpText` in `src/cli-style.ts` is read as a TypeScript AST, one
  section per `menu.section`, each `menu.row` a field, and an argument that
  is not a string literal or a template whose only hole is `CLI` (from
  `src/branding.ts`) fails the run, naming its line. `diagnostics.md` has a
  card per band, and `diagnostics/nl<band>xxx.md` lists the band's codes,
  each under its own heading: band 0 from the constants of `src/codes.ts` and their
  doc comments, every other code from its four rule tables with its
  fragment, each `tests/wordings/nl####_*.ts` example with its `.err`, and
  the reason `tests/wordings/unreachable.txt` gives for a code no program
  provokes. The run fails unless the band pages render `RULE_COUNT` plus
  four codes between them.

A module's page is read from the `/** ... */` comment that opens its file.
For a `nish:` module it is the `/** ... */` comment right above its
`declare module "nish:x"` in `runtime/nish.d.ts`; a module without one (a
`//` comment does not count) opens with a fixed line naming the module
instead.

1. **The lead**, the first paragraph, opens the page. A leading
   `` `nish/x` — `` (or `nish/x:`) naming the module is dropped, since the
   title says it, and the first letter left is capitalised. Its first
   sentence is the module's line in `index.md`.
2. **The usage example** is the first code block (lines indented two spaces
   or more, not a list) that reads as code: its first line opens with a
   keyword (`import`, `export`, `const`, `let`, `var`, `function`, `class`,
   `type`, `interface`, `await`, `async`, `for`, `if`, `while`, `return`) or
   a `//` comment, whatever it imports. A diagram or a config before it
   (`PRK = HKDF-Extract(...)`, a JSON object) stays with its paragraph. The
   code blocks right after it, a blank line apart, join it. It is shown
   after the import line, fenced `ts` whether or not it parses, since an
   example may elide with `…`. Every other code block is fenced `ts` when it
   parses and `text` otherwise. A `ts` block is titled `example.ts` and
   wrapped in a `<scalar-code-group>` of one, since Scalar shows a block's
   title only as a code group's tab; a `text` block (a diagram, a table) has
   no title. Code blocks with only a blank line between them are one block.
3. A list or code block belongs to the paragraph before it, and so does a
   paragraph whose first line is indented one space past the comment's `* `
   (` *  More of the detail.`): a long detail or warning broken into
   paragraphs stays under its title.
4. **A warning** starts at any sentence that opens with bold text saying
   the module refuses, limits or caps something (`refus`, `limit`, `cap`),
   at the start of a paragraph or within one, and runs to the end of that
   paragraph and its lists and code blocks. It is a warning callout, split
   from the text before it, so a limit is never folded away. Rules 5 and 6
   apply to what precedes it. The rule reads the bold title only, not the
   sentence after it, so a hazard titled otherwise (bcrypt's **The cost comes
   from the hash.**) is a detail: a source that wants a hazard shown as a
   warning says so in its title.
5. **The paragraph after the lead** is the summary, shown as an info
   callout, unless it opens with a bold title (`**Title.** Body` or
   `**Title**: body`); then the page has no summary and the paragraph
   follows rule 6. A bold phrase that runs on into its sentence
   (`**The syntax is JavaScript's**, with …`) is not a title.
6. **A later paragraph opening with bold text** is a collapsible detail
   titled with that text, code spans kept as written (a title attribute
   holds no Markdown). `**Title.** Body` or `**Title**: body` uses the
   rest as the body; otherwise the whole paragraph is the body.
7. Every other paragraph is shown as written.

## Tooling for these docs

- `node scripts/gen-reference.mjs` regenerates `docs/reference/` and its
  routes; `--check` fails when either is stale (see
  [The library reference](#the-library-reference)).
- `docs/cookbook/regen.sh` rebuilds every IR listing in IR_COOKBOOK.md from
  `docs/cookbook/*.ts`; `--check` fails when the doc is stale.
- `node docs/check-links.mjs` verifies every relative link, every link to
  this repository at `github.com/amritk/nish/blob/main/`, and their heading
  anchors in `README.md`, `CHANGELOG.md`, and `docs/**/*.md`; that a routed
  page links only routed pages relatively, with anchors that land on the site
  too; and that
  `scalar.config.json`'s routes and the pages under `docs/guide/` match.
