# Binding a C library: `nish c-import`

Calling a C library means writing a `declare function` for each function you
call, a `declare class` for each struct it reads, and a constant for each
`#define` and enum you pass. `nish c-import` writes that module for you from
the library's header, and lists what it could not bind. You check the module
in and import it like any other; the header is only read again when you
regenerate.

```console
$ nish c-import wc.h -o wc.ts
```

The declarations it writes are the ones
[Calling Nish from other languages](interop.md#calling-c-from-nish-declare-function)
describes, under the rules of
[LANGUAGE.md → Calling C](../../reference/language/declarations.md#calling-c).
The command needs `clang`: it is clang that reads the header, with the same
preprocessor and the same answers about sizes your C compiler gives. Set `CC`
to use another clang.

## What it writes

Given this header:

```c
#include <stddef.h>
#include <stdint.h>

#define WC_MAX_WORD 64
#define WC_NAME "wc"
enum wc_mode { WC_BYTES, WC_WORDS = 2 };

typedef struct counter counter;
struct wc_span { int64_t start; int64_t len; };

counter *wc_new(enum wc_mode mode);
int wc_feed(counter *c, const char *text);
int64_t wc_total(counter *c, int64_t *words);
int wc_last(counter *c, struct wc_span *span);
char *wc_report(counter *c);
void wc_free(counter *c);
void wc_free_report(char *r);
int wc_log(const char *format, ...);
```

On an x86-64 Linux machine, `nish c-import wc.h -o wc.ts` writes:

```ts wc.ts
// Generated by nish c-import from wc.h. Do not edit; regenerate it.
// Target: x86_64-unknown-linux-gnu
// Data model: LP64
// Regenerate: nish c-import wc.h --target x86_64-unknown-linux-gnu -o wc.ts

declare class OutI64 {
  value: i64
}

export declare class counter {}

declare class wc_span {
  start: i64
  len: i64
}

export const WC_BYTES: i32 = 0
export const WC_WORDS: i32 = 2
export const WC_MAX_WORD: i32 = 64
export const WC_NAME: string = "wc"

export declare function wc_new(mode: i32): counter | null
export declare function wc_feed(c: counter, text: string): i32
declare function wc_total(c: counter, words: OutI64): i64
declare function wc_last(c: counter, span: wc_span): i32
export declare function wc_report(c: counter): CPtr | null
export declare function wc_free(c: counter): void
export declare function wc_free_report(r: CPtr): void

/* Not bound:
 *   wc_log: variadic
 */
```

Each part of the header becomes one kind of declaration:

| In the header | In the module |
| --- | --- |
| a function | a `declare function` with the same name, exported unless it takes an out class or a struct with fields |
| a struct of numbers and pointers | a `declare class` with the same fields; a pointer field is `CPtr \| null` |
| a fixed-length array field of numbers (`uint32_t h[8]`) | a field of type `Record<integer<0, 7>, u32>`, indexed `d.h[i]` |
| a struct the header only names (`typedef struct counter counter`) that a bound function returns | an exported opaque class, `export declare class counter {}`: a pointer to it is a `counter` |
| an enum constant, an integer `#define` | an `export const` of `i32`, `u32`, `i64` or `u64`, by the C type of the constant or of its enum |
| a string `#define` of printable ASCII | an `export const` of `string` |
| a pointer to a number a function writes into (`int64_t *`) | an out class, `OutI64`, with one `value` field |
| a `/** … */` comment just before a function, struct, enum constant or `#define` | the same comment, on the declaration it writes |

The C integer types become the Nish width of the same size and sign on the
target: `int` is `i32`, `int64_t` and `long long` are `i64`, `size_t` is `u64`
on a 64-bit target and `u32` on wasm32. `float` and `double` are `f32` and
`f64`. A `_Bool` parameter or result is `boolean`; a struct with a `_Bool`
field and a pointer to `_Bool` are not bound.

The defaults for pointers are the safe ones:

- A `const char *` parameter is a `string`, which is never null; a
  `const char *` result is `string | null`. Where the C function accepts
  `NULL`, say so with `"nullable": true` (below).
- A pointer to a struct the header defines, and the command binds, is the
  struct's class as a parameter, never null unless the overrides file says
  `"nullable": true`. As a result it is a `CPtr | null`. A defined struct the
  command does not bind (a bitfield, a union, a packed layout, an array it
  cannot hold) stays a `CPtr` both ways.
- A pointer to an opaque struct (below) is its class both ways: never null
  as a parameter unless the overrides file says `"nullable": true`, and
  nullable as a result (`counter | null`).
- A struct the header only names is an opaque class of its own, so a
  `counter` cannot be passed where a `chan` is wanted, and neither can a
  `CPtr`. It stays a `CPtr` where a class cannot stand for it, and the
  comment at the end of the module says which. For example: no bound
  function returns it
  (no value of the class could exist), a function takes a pointer to a
  pointer to it (`counter **`, which only an `OutPtr` holds), a result is
  `"owned"` (below), a struct's field points to it, or its name is taken by
  another declaration (or is not a name Nish can write).
- Any other `char *` result is a `CPtr | null`: the module cannot know
  whether you must free it.
- A `void *` or `unsigned char *` parameter is a `CPtr | null`, or a `CPtr`
  when the header marks it `_Nonnull`.
- A `const` pointer to a number (`const int64_t *`) is a `CPtr | null`, not an
  out class: C reads it and does not write it. A pointer to a `const` pointer
  (`char *const *`) is a `CPtr | null` for the same reason.
- A non-`const` pointer to a number (`int64_t *`) or to a pointer is an out
  class, such as `OutI64` or `OutPtr`, which C writes into. An array
  parameter (`int64_t counts[4]`) is a pointer in C, so it is an out class
  too.
- Clang's `_Nonnull` and `_Nullable` on the outermost pointer of a parameter
  or result set its nullability (a `_Nullable` parameter is `string | null`
  or `CPtr | null`, with no override needed); on an inner pointer
  (`const char * _Nonnull *`) they change nothing.

A module that uses an out class or a struct declares it itself. A class name
is unique across a program, so two generated modules that both declare
`OutI64`, or the same struct, cannot be built together (the second is
refused). To bind two libraries for one program, write a header that includes
both and generate one module from it, with `allow` naming both libraries'
functions.

## Using the module

Import what you need and call it as you would any declared function. The
library is linked the way any other C your program calls is, as
[Calling Nish from other languages](interop.md#calling-c-from-nish-declare-function)
shows:

<!-- nish:ok -->
```ts
declare class OutI64 {
  value: i64;
}

declare class counter {}

declare function wc_new(mode: i32): counter | null;
declare function wc_total(c: counter, words: OutI64): i64;
declare function wc_free(c: counter): void;

export const WC_WORDS: i32 = 2;

export const count = (): i64 => {
  const c = wc_new(WC_WORDS);
  if (c === null) {
    return toI64(-1);
  }
  const words = new OutI64();
  const bytes = wc_total(c, words);
  wc_free(c);
  const wordCount = words.value;
  // C's answers are counts; testing both against a bound before adding
  // them is what proves the sum fits.
  if (bytes < 0 || bytes > 1000000000 || wordCount < 0 || wordCount > 1000000000) {
    return toI64(-1);
  }
  return bytes + wordCount;
};
```

### Importing the bindings from another module

The module exports each binding another module can use: the opaque classes,
the constants, and every function whose parameters and result are numbers,
strings, `CPtr` or opaque classes. Import them by name, as you would any
export. An opaque class is named, as in its own module, only on a local a
binding fills. The importer calls C, so it is charged the `ffi` capability that
[`--deny ffi`](cli.md#asking-what-a-program-can-do) refuses:

<!-- nish:ok -->
```ts wc.ts
export declare class counter {}

export const WC_WORDS: i32 = 2

export declare function wc_new(mode: i32): counter | null
export declare function wc_feed(c: counter, text: string): i32
export declare function wc_free(c: counter): void
```

<!-- nish:ok -->
```ts words.ts
import { counter, wc_feed, wc_free, wc_new, WC_WORDS } from "./wc";

export const words = (text: string): i32 => {
  if (text.indexOf("\u0000") >= 0) {
    return -1;
  }
  const c: counter | null = wc_new(WC_WORDS);
  if (c === null) {
    return -1;
  }
  const n = wc_feed(c, text);
  wc_free(c);
  return n;
};
```

A function that takes an out class or a struct with fields (`wc_total`,
`wc_last` above) is not exported: a struct's layout is built and read only in
the module that declares it. Call it there, from a function of your own in
that module, or generate the module with `allow` naming only the functions a
program imports.

## What is not bound

The comment at the end of the module names every function, struct and macro
the command skipped, and why. Nothing is skipped silently. What it does not
bind today:

- a variadic function (`printf`), one that takes a `va_list`, one that takes
  or returns a function pointer (a callback), and a `static` or `inline`
  function, which has no symbol to link;
- a function that takes or returns a struct by value, not through a pointer;
- a function-like macro, a macro whose value is not an integer or a string,
  an integer macro wider than 8 bytes (`((__int128)1)`), and a string macro
  with an escape, two pieces or a byte that is not printable ASCII (`"café"`);
- a union, a struct with a bitfield, a packed struct or one with an
  `aligned` attribute or under `#pragma pack`, whose layout a `declare class`
  cannot copy;
- a struct with an array field whose element is not an `i32`, `i64`, `u8`,
  `u16`, `u32`, `u64`, `f32` or `f64` (an array of pointers, structs, arrays,
  `_Bool`, plain `char` where the target makes it signed, or an `aligned`
  typedef; on AArch64 Linux an array of plain `char` is a `u8` array), a
  flexible array
  member (`int data[]`) and a zero-length array;
- `long double`, `__int128` and `_Complex`, in any spelling or word order;
- `signed char` and `short`, which have no Nish width, and a plain `char`
  where the target makes it signed;
- a type clang does not resolve to one of the above, an unnamed struct,
  union or enum, a `typeof` type, and a type with an attribute;
- an enum whose values need more than 4 bytes, and a packed enum, narrower
  than an `int`; an enum constant above 2^63 is listed too;
- a function declared with an `asm` label (`int f(void) __asm__("g")`) or
  an `alias` attribute, whose symbol is not its name;
- a function declared `_Noreturn` or `noreturn`, with a calling convention
  other than the C default (`ms_abi`), with another attribute in its type,
  or without a prototype (`int f()`, which C17 reads as unknown parameters);
- a variable (`extern int counter`);
- a name that is not an ASCII identifier: clang accepts `$` and Unicode
  letters in a C name (`get$value`, a Cyrillic `а` in `pаss`), which a Nish
  module does not copy. The declaration is listed, or the struct holding the
  field, and a name that is not printable ASCII is shown as `a declaration
  whose name is not printable ASCII`;
- a name Nish reserves (`eval`, `Array`, an out class name such as `OutI64`),
  and a name two declarations want: a function and a struct both called
  `stat`, or a macro with an enum constant's name. The function, then the out
  class, then the struct, then the enum constant, then the macro keeps it; the
  others are listed. A parameter with a reserved name is renamed with a
  trailing `_` instead;
- a function from another header the first one includes, unless `allow`
  names it (below). These are not listed: only the header's own functions
  are, including those `allow` leaves out. A struct from an included header
  is never a `declare class`: a pointer to it is a `CPtr`.

Write those by hand, beside the generated module, in a file of your own.

## Overrides: what the header cannot say

A header does not say whether a pointer may be `NULL`, whether a result must
be freed, or which parameter is a buffer's length. An overrides file, in JSON,
says so; pass it with `--overrides`:

```json wc.overrides.json
{
  "header": "wc.h",
  "allow": ["wc_*"],
  "functions": {
    "wc_new": { "return": "nonnull" },
    "wc_report": { "return": { "owned": "wc_free_report" } },
    "wc_feed": { "text": { "nullable": true } }
  }
}
```

- `header` is the header this file is for; a different header is refused.
- `allow` lists the functions to bind, as globs (`*` matches any run of
  characters, `?` any one character). Without it, every function in the header itself is bound;
  with it, only the functions it names are, from whatever header declared
  them, and every other function is listed as not bound. It does not select
  structs, enums or macros: those still come from the header itself.
- `functions` sets, per function:
  - `"return": "nonnull"`, for a pointer result C never returns as `NULL`.
    `"return": "nullable"` is always refused: a pointer result is already
    nullable unless the header marks it `_Nonnull` or `returns_nonnull`, and
    the overrides file cannot overrule the header;
  - `"return": { "owned": "<free function>" }`, which records above the
    declaration which function frees the result;
  - per parameter, by name (an unnamed parameter is `arg0`, `arg1`, ... by
    its position, as the module writes it): `"nullable": true` for a pointer the defaults
    bind as never null (only `true` changes anything), and
    `"buffer": "<length parameter>"`, which binds a `void *` or `char *` and
    its length as a `u8[]` (a `readonly u8[]` when the header says
    `const void *`, so `"readonly"` is never needed and is refused), and a
    `uint16_t *`, `uint32_t *`, `int32_t *` or `float *` as a `u16[]`,
    `u32[]`, `i32[]` or `f32[]` whose length counts elements. A
    `size_t` length straight after the buffer on a 64-bit target keeps the
    plain form, `(data: u8[], len: u64)`. Any other length -- a `uint32_t`,
    `uint16_t` or `uint8_t`, one before the buffer, or a `uint32_t *` the
    function writes, bound as an out class such as `OutU32` (`OutU8` for an
    `unsigned char *`) -- is named on the buffer,
    `(len: u16, data: CountedBy<readonly u8[], "len">)`, and the call checks
    it against the buffer's length before C runs. The length must be one of
    those unsigned widths, by value or through a pointer the function writes;
    a signed one, the buffer itself, another buffer, or a name that is not a
    parameter is refused. The command never guesses a length from a parameter's name, and
    clang 18 drops the header's own `__counted_by` from a parameter, so the
    overrides file is where a pairing is said.

With this file, `wc_new` returns `counter` rather than `counter | null`, `wc_report` carries the comment
`// The result is owned: free it with wc_free_report.`, and `wc_feed` takes
`string | null`. An override that would change nothing is refused, so a
renamed C function cannot leave a stale override behind: one that names a
function, a parameter or a free function the header does not have, a function
that is not bound (variadic, `static`, declared with an `asm` label, outside
`allow`, or not in the header), a file with neither `allow` nor `functions`,
an empty `functions`, an empty object for a function or a parameter, `"nullable": false`, `"readonly": false`, an empty
`"buffer"`, `"nullable"` with `"buffer"`, an `allow` glob that matches no
function, `"nullable"` on a parameter already bound as nullable or as an out
class or marked `_Nonnull` in the header, a `"return"` that asks for what the
result already is, an `"owned"` free function that is not bound, or a key
written twice in one object. Each function's override is checked once
`allow` is read, wherever the keys sit in the file, against the declaration
the module would write without it.

A refused override is a plain `c-import:` or `overrides:` message on stderr
with exit code 1, like the command's other refusals; it carries no `NL` code,
since codes name diagnostics in a Nish program and an overrides file is not
one.

## Targets and the data model

A C type's size depends on the target: `long` is 64 bits on 64-bit Linux and
macOS and 32 bits on wasm32. The module records the target
and its data model in its first lines, and its `Regenerate:` line is the
command that wrote it, with the header and overrides paths as you gave them
and `-o` naming the module's file alone, so run it from the directory that
holds the module. `--target <triple>` writes the module for another
target; without it, the module is for the machine you run the command on.

A build for a target with another data model refuses a generated module
(NL3062), instead of calling C with the wrong widths:

```console
$ nish c-import limits.h --target wasm32-unknown-unknown -o limits.ts
$ nish main.ts
limits.ts:3:16: error: this module was written by nish c-import for ILP32, and this build is LP64: ...
```

Regenerate the module with `--target` for that build, and keep one module per
data model if you build for both.

## Exit codes

| Code | Meaning |
| --- | --- |
| 0 | the module was written |
| 1 | refused: the header or overrides file cannot be read, `-o` is the header itself or the overrides file, a scratch directory cannot be made beside the output, a path holds a quote, a backslash, a comment delimiter or a byte that is not printable ASCII, clang rejected the header, or an override is wrong |
| 2 | usage: no header, no `-o`, an unknown flag or target |
| 3 | `clang` (or `CC`) cannot run |

On a refusal nothing is written, so a failed regeneration leaves the checked-in
module as it was.
