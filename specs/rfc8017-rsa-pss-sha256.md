--- abstract

A profile of RFC 8017 for the signing functions of nish/crypto/rsa-sign:
RSASSA-PSS with SHA-256 and MGF1 with SHA-256, the scheme TLS 1.3 names
rsa_pss_rsae_sha256 (RFC 8446 Section 4.2.3), over the RSASP1 primitive
with a private key of 2048 to 4096 bits. Every requirement quotes RFC 8017,
the main source, or RFC 8446; every binding sentence of RFC 8017 (MUST,
MUST NOT, SHALL, SHALL NOT, REQUIRED) is tested or excluded here.

--- middle

# Introduction

{::boilerplate bcp14-tagged}

nish/crypto/rsa-sign signs with RSASSA-PSS (RFC 8017 Section 8.1.1), its
encoding EMSA-PSS (Section 9.1.1) with Hash SHA-256 and MGF MGF1 with
SHA-256 (Section B.2.1), so hLen is 32, over RSASP1 in the first form (n, d)
of the private key (Section 5.2.1). `rsaParsePrivateKey` reads a DER
RSAPrivateKey (Section A.1.2) from `der[start, end)` and returns the key as
a `Secret`: the modulus n, the private exponent d and the public exponent
e, each as k big-endian octets, where k is the octet length of n, in that
order, 3k octets in all. It refuses, with null, anything but a version 0
key whose n is odd and of 2048 to 4096 bits, whose e is odd and in
[3, 2^32), and whose d is in (0, n). The properties see the key as bytes.

`rsaSignRaw(key, m)` is RSASP1: m is k octets, and the result is
m^d mod n as k octets, or null when m is not k octets or not below n. It
checks its result by raising it to the third slot, e, so the key with its
second and third slots swapped, `concat(n, concat(e, d))`, computes s^e mod n, the
verification primitive RSAVP1 (Section 5.2.2). The properties recover the
encoded message of a signature that way and check every field of it.

`rsaSignPssSha256Salted(key, msg, salt)` signs msg with the salt it is
given, so sLen is the salt's length; `rsaSignPssSha256(key, msg)` signs
with a 32-octet salt, as TLS 1.3 asks, which it derives itself. Both return
the k-octet signature, or null.

Out of scope: RsaSignScratch, the reusable scratch of rsaSignPssSha256Into and rsaSignPssSha256SaltedInto, a class and not a function

Out of scope: rsaSignPssSha256Into, the same signature as rsaSignPssSha256 written into a caller's array through an RsaSignScratch, held by tests/link/crypto\_rsa\_sign; its first parameter is the class RsaSignScratch, which vector 0.6.0 refuses in a ts-interface block ("`RsaSignScratch` is not a ts-interface type; use u8[], string, boolean, i8, i16, i32, i64, u8, u16, u32, u64, f64, Secret<u8[]>, u16[], u32[], u64[], each optionally `| null`"), and it answers a boolean where an `/* out CAP */` write returns the end offset

Out of scope: rsaSignPssSha256SaltedInto, the same signature as rsaSignPssSha256Salted written into a caller's array through an RsaSignScratch, for the reasons rsaSignPssSha256Into is

Out of scope: RSA\_SIGN\_MIN\_BITS, an `i32` constant a vector or property cannot call; P-KEY-2048 holds the smallest modulus accepted

Out of scope: RSA\_SIGN\_MAX\_BITS, an `i32` constant a vector or property cannot call; P-KEY-4096 holds the largest modulus accepted

Out of scope: RSA\_PSS\_SHA256\_SALT\_SIZE, an `i32` constant a vector or property cannot call; P-TLS-SALT holds the 32-octet salt

# Known Answers

RFC 8017 prints no RSASSA-PSS signature, so each expected signature below
is recomputed by `--run-sources` from the command in its Source cell:
`specs/rfc8017-rsa-pss-sha256.kat.py`, an implementation of Sections
8.1.1, 9.1.1, B.2.1 and 5.2.1 over Python's integers that uses the
standard library only and shares no code with nish/crypto/rsa-sign. Each
signature was also checked, when this spec was written, with the
RSASSA-PSS verification of the Python `cryptography` package. The key
argument is the private key as `rsaParsePrivateKey` returns it: n, d and
e, each k octets. The three keys were made for this spec: the 2048- and
4096-bit keys by OpenSSL, and the 2049-bit key, whose encoded message is
one octet shorter than k, from two 1025-bit primes, since OpenSSL rounds
the size of a key it generates. None of them signs anything outside these
tests. Each key signs the message "nish rsa-pss" with the salt 00 to 1f,
and the empty message with the empty salt, each
"" (0 octets).

# Out of Scope

RFC 8017 prints no RSASSA-PSS signature, so the vectors of Known Answers
take their expected values from a command, not from the RFC.

Verification is not a property here: `rsaVerifyPss` in nish/crypto/rsa
takes the class RsaPublicKey, which vector 0.6.0 refuses in a ts-interface
block. The properties run RSAVP1 through `rsaSignRaw` instead, under the
swapped key, and check the encoded message field by field, which is what
EMSA-PSS-VERIFY (Section 9.1.2) checks.

The salt of `rsaSignPssSha256` is not random (Section 9.1.1 step 4): it is
derived from the private key and the message, so the signature is the same
for the same key and message. Its derivation is an implementation choice
that RFC 8017 does not constrain, so no property fixes it; P-TLS-SALT holds
that the salt it uses is 32 octets and that the signature is the one
`rsaSignPssSha256Salted` makes with that salt.

The message-too-long errors (Section 8.1.1 step 1 and Section 9.1.1 step 1)
need a message of 2^61 octets, and MGF1's mask-too-long error (Section
B.2.1 step 1) a mask of 2^37 octets; neither can be built, so neither is
tested. RSASP1's second form (p, q, dP, dQ, qInv) is not used: the key is
kept as (n, d), and the result is the same integer.
